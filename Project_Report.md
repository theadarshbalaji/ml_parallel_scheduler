# Technical Project Report: ML-Based Parallel Task Scheduler (CPU)

**Date:** December 30, 2025  
**Domain:** System Architecture, Multi-core Computing, and Applied Machine Learning  

---

## Abstract
This project presents the design, implementation, and rigorous evaluation of a Machine Learning (ML)-assisted parallel task scheduler for multi-core CPUs. The primary objective is to investigate the efficacy of ML-based scheduling decisions compared to traditional heuristics like First-In, First-Out (FIFO) and Random scheduling. Utilizing real executed workloads and actual runtime measurements, the project identifies the critical conditions under which an ML-guided approach provides tangible performance benefits, and conversely, where it introduces detrimental overhead. The findings demonstrate a significant non-monotonic scaling behavior, emphasizing that intelligent scheduling is most advantageous in resource-constrained environments.

---

## 1. Introduction and Project Motive

Modern operating systems and cloud computing environments rely heavily on efficient task scheduling to maximize resource utilization and minimize execution time (makespan). Traditionally, schedulers utilize rule-based algorithms such as FIFO, Round-Robin, or Longest Processing Time (LPT) due to their low computational overhead and simplicity. 

The core motive of this project is to quantitatively answer a fundamental systems design question: **Under what conditions does Machine Learning actively improve task scheduling in highly parallel systems, and when does it fail?** 

Rather than working under the assumption that ML universally enhances system performance, this project intentionally stress-tests the scheduler across varying degrees of parallelism. By prioritizing empiricism over theoretical assumptions, this work aims to provide actionable engineering insights into the trade-offs between scheduling intelligence and computational overhead.

---

## 2. System Architecture and Task Design

The project is built around a configurable multi-threaded simulation that executes genuine computational workloads.

### 2.1 Workload Types
The scheduler processes three distinct types of independent tasks:
1. **CPU-Bound Tasks:** Matrix multiplication operations built to heavily utilize the processor.
2. **IO-Bound Tasks:** File read/write operations designed to simulate disk latency and bottlenecks.
3. **Mixed Tasks:** A combination of compute and IO operations.

Crucially, **no artificial sleep calls or simulated delays are used**. All measured times reflect the actual physical execution of the computational logic.

### 2.2 Task Features
To mimic the inputs available to a modern OS scheduler, each task is parameterized by a set of dynamic features:
- **`inputSize`:** The size/complexity of the workload (e.g., matrix dimensions).
- **`opType`:** The classification of the task (CPU, IO, or MIXED).
- **`actualRuntimeMs`:** The ground-truth measured execution time.
- **`predictedRuntimeMs`:** The inference value generated by the ML pipeline.

---

## 3. Implementation of Scheduling Strategies

The system implements three distinct scheduling logic paths:

1. **FIFO (First-In, First-Out) Scheduler:** Acts as the primary baseline. Tasks are queued and executed strictly in their arrival order.
2. **Random Scheduler:** Tasks are arbitrarily shuffled prior to execution. This establishes a baseline for scheduling randomness and variance.
3. **ML-Based Scheduler:** A regression model predicts the execution time (`predictedRuntimeMs`) of each incoming task based on its features. The scheduler then sorts the task queue in descending order of predicted runtime, prioritizing the longest tasks first to prevent tail-end stragglers from delaying the overall completion time, drawing inspiration from LPT heuristics.

---

## 4. Experimental Setup

To evaluate the respective schedulers, experiments were run systematically under the following conditions:
* **Hardware Profile:** Multi-core CPU system.
* **Dataset:** A test suite of approximately 300 uniquely parameterized real tasks. The exact same queue of tasks is fed to all three schedulers to ensure a fair comparison.
* **Parallelism Levels:** The schedulers were tested at 2, 4, 8, and 16 active threads to observe scaling behavior.
* **Primary Metric:** Total Execution Time (Makespan), measured in milliseconds. This is the definitive metric for throughput in batch-processing systems.

---

## 5. Results and Critical Analysis

The collected data highlighted a profound "diminishing returns" effect regarding the viability of ML scheduling. 

### 5.1 Performance Data Summary (Makespan)

| Thread Count | FIFO Scheduler (ms) | Random Scheduler (ms) | ML Scheduler (ms) |
|--------------|---------------------|-----------------------|-------------------|
| **2 Threads**| 624                 | 570                   | **502**           |
| **4 Threads**| 265                 | 255                   | **241**           |
| **8 Threads**| 153                 | 153                   | **150**           |
| **16 Threads**| **115**            | 117                   | 148               |

*Note: Lower execution time is optimal.*

### 5.2 Insight 1: ML Excels at Low Parallelism (2–4 Threads)
At 2 and 4 threads, the system is highly resource-constrained. Because only a few instructions can be processed at once, executing a computationally massive task at the end of the queue leaves all other threads idle, catastrophically increasing the makespan. 
* **The Result:** The ML scheduler's ability to predict and front-load heavy tasks yields a commanding 10% to 20% speedup over the FIFO baseline. 

### 5.3 Insight 2: Convergence at Moderate Parallelism (8 Threads)
As available threads increase, CPU utilization naturally rises. The penalty for poor task ordering is masked by the sheer volume of concurrent execution. 
* **The Result:** The performance delta between the ML scheduler and the simple heuristics narrows to a marginal 1-3%. The intelligence of the ML model begins to face diminishing returns.

### 5.4 Insight 3: The Failure of ML at High Parallelism (16 Threads)
At 16 threads, the ML scheduler actively degrades system performance, falling roughly 28% behind the simple FIFO algorithm. This inversion is driven by three fundamental systems effects:
1. **Scheduling Overhead:** At high parallelism, tasks are dispatched almost instantly. The time required to run the ML inference, extract features, and execute the sorting logic exceeds the actual computation time of the smaller tasks. 
2. **The Ceiling Effect:** With rapid, asynchronous execution, thread idle time is practically non-existent. Without idle time to optimize, the ML model is attempting to solve a bottleneck that no longer exists.
3. **Costly Prediction Errors:** In highly volatile, massively parallel environments, minor inaccuracies in the regression model compound quickly without the room for error correction present in slower, sequential execution.

---

## 6. Conclusion and Engineering Takeaways

This project successfully proves that Machine Learning is an incredibly powerful tool for task scheduling, but only when applied under the correct architectural constraints. 

**Key conclusions:**
* **Resource Scarcity is the Catalyst:** ML-assisted scheduling should be aggressively pursued in environments characterized by diverse, heterogeneous workloads and limited concurrent processing power (e.g., edge devices, heavily partitioned virtual machines).
* **Simplicity Scales Better:** For high-throughput, massively parallel systems (like high-end servers or vast cloud instances), the pure, uninhibited speed of traditional low-overhead heuristics like FIFO remains undeniably superior.

Ultimately, diagnosing when to bypass complex ML logic in favor of straightforward, deterministic algorithms is a hallmark of mature systems engineering—a principle clearly demonstrated by the results of this project.
